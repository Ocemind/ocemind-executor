## 0. 一句话结论

规格里列的 16 个能力**不是 16 个并列模块**，而是 **1 个执行内核 + N 个适配器**。
Timi 下载器已经有那个内核了。所以正确做法不是"再写一遍 16 个模块"，而是
**把现有内核从"下载专用"泛化成"任务执行通用"，再把能力一个个注册进去**。

按这个口径重新算账：16 个能力里

| 分类 | 数量 | 说明 |
|------|------|------|
| 已实现 | 3 | 下载、后台任务队列、桌面壳 |
| 只差一层 ffmpeg 参数封装 | 5 | 媒体转码、音频后期、字幕、素材合成、图像基础处理 |
| 需要新引擎（但都是新文件，不动老代码） | 4 | ASR、文档解析、OCR、AI 生图/TTS |
| 受外部条件限制 | 3 | 浏览器发布（分三档）、视频号（不做抓取）、视频镜头生成（贵） |
| 明确不做 | 1 | 无限画布（规格自己写的） |

也就是说：**12 个不需要新架构，4 个是插进来的新文件，0 个需要推倒重来。**

## 2. 六个问题的解决方案

### 问题一：规格承诺"跨平台打包"，但本机智能应用控制会拦掉新 exe

**这已经不是问题了——仓库里有验证过的答案。**

`tools/make_launcher.py` 生成一个快捷方式，指向 Python 官方签名的 `pythonw.exe`
跑 `run.py`。签名的解释器本身在微软信誉库里，不受 SAC 约束，而且永远是最新代码，
不用每改一次就重新攒一次信誉。

**方案：**

1. Windows 侧维持现状，**不打包**。启动器生成器已经存在。
2. 规格里的"跨平台"改写成 **"源码分发 + 各平台原生启动器"**：
   - Windows：`make_launcher.py` → 桌面快捷方式（已有）
   - Ubuntu：新增 `tools/make_desktop_entry.py` → 写 `~/.local/share/applications/ocemind.desktop`
3. 如果将来确实需要单文件分发，唯一可行路径是 **代码签名**（Azure Trusted
   Signing / 商业证书），成本几百到几千元/年。**写进风险清单，不写成承诺。**

> 附带收益：源码启动意味着改一行代码重启就生效。打包的版本永远要追着重新打包。

---

### 问题二："自动发布到各平台"撞上平台 API 现实

**方案：把发布拆成三档，写进代码而不是写进文档。**

| 档 | 平台 | 机制 | 自动化程度 |
|----|------|------|-----------|
| A | YouTube、X | 官方开放 API（需要开发者资质/申请） | 可全自动 |
| B | B站、小红书 | Playwright 驱动浏览器，账号已登录 | **必须人工确认后点击** |
| C | 视频号 | 无稳定接口 | **不支持自动，只导出发布包** |

关键设计——规格要求的"发布批准绑定版本/快照"落地为：

```
POST /api/publish/{job_id}/approve
body: { snapshot_hash: "<sha256 of the exact output files>" }
```

服务端重新计算产物哈希，**不一致直接 409 拒绝**。这样"批准"这件事在物理上
绑死在那份产物的字节上，改一个字符都过不去。这是规格那句话唯一可信的实现方式。

另外：不做"一键全平台"按钮，做 **"导出发布包"**（文件 + 元数据 JSON + 封面）。
这是合规、稳定、且对所有平台都成立的中间态。

---

### 问题三：视频号抓取是不可控风险

**方案：换入口，不换目标。** 用户真实需求是"视频号的内容变成文本"，不是
"必须用链接"。所以：

- "链接 → 视频文件"这一环：视频号**明确标注不支持**（yt-dlp 无适配器，
  逆向方案随版本随时失效）
- "文件 → 文本"这一环：完全支持。用户手动保存/录屏后拖进执行器即可

这样产品仍然交付了价值，但把不可控的外部依赖从主路径上摘掉了。UI 上给这条
写清原因，避免用户以为是 bug。

---

### 问题四：能力清单会变成"文档说支持，实际不支持"

**方案：能力清单是代码里的注册表，不是 md 文件。**

新增 `xiaoe_dl/engines/registry.py`：

```python
@dataclass(frozen=True)
class Capability:
    id: str                      # "asr.transcribe"
    name: str                    # "语音转文字"
    kind: str                    # 与任务类型对应
    backend: str                 # "local" | "cloud"
    requires_gpu: bool
    paid: bool
    automation: str              # "auto" | "assisted" | "manual"
    params_schema: dict
    test_status: str             # 由测试自动写回，不手填
```

`GET /api/capabilities` 返回的就是这份数据。**UI 从它渲染，Agent 从它发现能力，
文档从它生成**——单一事实源，三处不可能不一致。

`test_status` 由 `tests/test_capabilities.py` 里的 smoke 用例跑通后写回
`green`，跑不通就是 `red`。**不允许手填。**

### 问题五："只做适配器"低估了基础设施，实际占一半

**方案：不辩解，直接量化。** 上面第 1 节已经算过：基础设施 60% 已完成，
剩余四项：

| 待补 | 为什么不能省 | 预估 |
|------|-------------|------|
| 任务 DAG（派生产物） | 下载完要能直接接 ASR，否则用户得手动搬文件 | ~150 行 |
| 预算门控 | 规格明确要求"在代码里强制"，付费能力必须先有钱包 | ~120 行 + SQLite |
| 能力注册表 | 见问题四 | ~100 行 |
| 对外 API 鉴权 | 规格要求 Agent 能接入 | ~80 行 |

合计约 450 行新代码，**不改动** `manager.py` 的核心调度逻辑。

关于"不分阶段、一次全做完"：这里不规划阶段，改为**定义第一个可验收交付**——
语义上是验收标准，不是排期：

> **垂直切片**：一条链接进来 → 自动下载 → 自动转写 → 落地 `.srt` + `.md`，
> 全程在同一个任务列表里看到状态，中途可暂停可续传。

这条链跑通了，剩下的就是往注册表里加条目。链没跑通，加再多适配器也没意义。

---

### 问题六：Windows + Ubuntu 双机重复建设

**方案：单机为主，远程只承担重计算。**

- Windows：UI + 轻任务（下载、ffmpeg、文档解析）
- Ubuntu（`100.92.164.104`）：GPU 任务（本地 ASR、本地图像模型）
- 通信：HTTP + token，走 Tailscale 网段

**硬约束（来自你的明确要求）：**

- **不修改 `sshd` 任何配置，不占 22 端口，不动现有 SSH 会话**
- 执行器以 `systemd --user` 常驻，只监听 Tailscale 网卡上的端口
- 连接失败时 Windows 侧自动降级为本地/云端执行，**不阻塞主流程**

这样远程那台是"可选的算力"，不是"必须的第二套系统"。

## 3. 另外五个规格要求的具体落点

### 幂等（规格要求）

现在下载任务的 id 是随机 uuid（`manager.py:134`），只有课程有去重键
（`manager.py:126-132`）。**通用任务连点两下会重复下载。**

改成：

```python
idem = sha256(capability_id + canonical_params + input_fingerprint)[:16]
```

提交前扫一遍未完成任务，命中就返回已有任务而不是新建。`input_fingerprint`
对链接取 URL，对本地文件取内容哈希。

### 进度不造假（规格要求）

现有三种引擎的进度都是真实字节或真实分片数，天然合规。新能力里 ASR、生图
这类**总时长不可预知**，所以：

- `progress` 字段允许为 `null`
- `null` 时 UI 显示不确定态（跑马灯 + "已处理 3 分 12 秒"），**不画假百分比**

### 预算强制（规格要求）

`POST` 任何付费能力前先查当月累计；超预算返回 **402**，不是警告横幅。
记账落 SQLite（`%APPDATA%\xiaoe-dl\ocemind.db`），因为要按时间聚合，
`tasks.json` 那种全量重写不适合。

### Agent 接入与真实限制披露（规格要求）

- `xiaoe_dl/cli.py` 已有模式，扩成 `run.py --api ...` 即可
- MCP server = 这层 API 的 stdio 薄包装，约 20 行
- **必须明说**：云上的 Agent 打不到 `127.0.0.1`。Agent 必须跑在本机或
  Tailscale 内。这条要出现在能力清单和文档里，不能让用户自己撞墙

### 迁移包（规格要求）

导出 = 配置 + 能力开关 + **加密后的密钥**（复用现有 `crypto.py`）。
导入时按版本号迁移，版本不兼容就拒绝而不是半读半写。
